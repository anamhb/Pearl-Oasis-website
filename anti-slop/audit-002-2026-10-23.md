## Findings

### 18. Mobile Hero frame delivery is late under constrained CPU (HIGH, R-03)

R-03 requires the mobile experience to hold up as a first-class layout. The
current Hero maps scroll progress to a frame index without React state updates
and coalesces scroll work through one animation-frame callback. In the measured
runs, however, an exact target frame took 80.5-107.6 ms at p90 to become
visible. The current sequence is 70 JPEGs at 1280x720; each decoded RGBA frame
is approximately 3.52 MiB. Five layers had non-zero `naturalWidth` at the end
of each run, approximately 17.58 MiB of decoded pixel data, with one layer
visible.

#### Measured evidence

Both runs used the current Hero on localhost, CPU throttling at 4x, disabled
browser cache, and scripted wheel input. The network was local and was not
throttled to a 4G profile.

| Metric | 320x568 | 390x844 |
|---|---:|---:|
| Hero scroll distance | 1300 px | 1932 px |
| Target-to-visible-frame latency, p50 / p90 / max | 50.9 / 107.6 / 193.8 ms | 16.9 / 80.5 / 162.9 ms |
| Target-to-visible frame distance, p50 / p90 / max | 0 / 0 / 3 frames | 0 / 1 / 2 frames |
| `img.decode()` promise duration, p50 / p90 / max | 23.0 / 43.9 / 70.8 ms | 16.8 / 26.3 / 46.4 ms |
| Animation-frame interval, p50 / p90 / max | 48.6 / 78.5 / 849.2 ms | 49.1 / 81.0 / 970.5 ms |
| Long tasks during the scroll | 0 | 2; 103 ms total, 52 ms max |
| Frame assets requested / bytes transferred | 77 / 2.30 MB | 144 / 4.39 MB cumulative across both viewport runs |
| Decoded Hero images / visible images | 5 / 1 | 5 / 1 |

The start, fast reverse, and fast forward checks displayed frames 001, 001, and
070 respectively. The active image retained its natural 1280x720 dimensions.
No blank active image or missing Hero frame was observed. The lag metric is
derived from the active image and current scroll target; it is not a subjective
smoothness score or a physical-device result.

#### Interpretation and proposed next step

The decode timings and target-to-visible delays make full-resolution image
decode/delivery the best-supported Hero-specific bottleneck. They do not prove
that decoding alone causes the reported physical-device lag: `img.decode()`
duration includes browser scheduling, the animation-frame observer covers the
whole page, and the controlled runs did not produce a repeatable long-task
pattern. A separate 390x844 reduced-motion A/B changed rAF p50 from 49.1 ms to
26.9 ms while target lag remained similar (p90 1 frame in both runs). This
suggests other continuous page motion also competes for frame time, but does
not identify it as the cause or justify changing any out-of-scope section.

Before making a full portrait sequence, compare a small representative set
cropped from the **current 70-frame footage** at 426x720 against the existing
frames at 320x568 and 390x844. The crop can preserve the existing `object-fit:
cover` field of view at those widths. Measure framing, sharpness, decode time,
and the same scroll-to-frame metrics; create the full 70-frame mobile set only
if that test shows a meaningful benefit. Do not use the obsolete 299-frame
portrait footage.

No code or asset fix is approved by this report. Physical Android and iOS
validation remains outstanding.
